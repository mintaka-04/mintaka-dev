## 목적

본 테스트를 통해 Vercel 및 EC2 기반 시스템의 안정 구간, 성능 저하가 시작되는 임계 구간, 그리고 서비스가 정상적으로 동작하기 어려운 한계 구간을 구분하여 분석하는 것을 목표로 한다.

## 현재 인프라 스펙

| 항목 | 값 |
|------|-----|
| 인스턴스 | t3.micro |
| vCPU | 2 |
| 메모리 | 1GB |
| 디스크 | 8GB |
| 워커 | Python AI 워커 (Docker 컨테이너) |

## 모니터링 전략

인프라 구조가 EC2와 Vercel로 나뉘어 있어 각각 다른 방식으로 성능을 판단한다.

### EC2 — 리소스 기반

EC2는 인프라에 직접 접근 가능하므로 리소스 지표로 성능을 판단한다.

| 지표 | CloudWatch 경로 |
|------|----------------|
| CPU 사용률 | AWS/EC2 → CPUUtilization |
| 메모리 사용률 | CWAgent → mem_used_percent |
| 디스크 사용률 | CWAgent → disk_used_percent |

### Vercel — 사용자 응답 기반

Vercel은 관리형 플랫폼이라 서버 리소스에 직접 접근할 수 없다. 사용자 관점의 응답 지표로 성능을 판단한다.

| 지표 | 설명 |
|------|------|
| 요청 수 | 단위 시간당 들어오는 요청 수 |
| 응답 시간 | 요청 → 응답까지 걸리는 시간 |
| 에러율 | 전체 요청 중 에러(4xx/5xx) 비율 |
| 함수 실행 시간 | Serverless Function 처리 시간 (AI 워커 연동 지연 파악 가능) |

## 관찰 지표

| 지표 | 설명 |
|------|------|
| 지연율 (avg, p95) | 평균 및 상위 5% 응답시간 |
| 에러 발생률 | 전체 요청 중 실패 비율 |
| WebSocket 끊김 빈도 | CloudWatch 로그에서 watchdog 재연결 로그 발생 여부 |
| 리소스 사용량 | EC2 CPU / 메모리 / 디스크 |

## 테스트 시나리오

### 실행 순서

베이스라인 → 점진적 부하 → 스파이크 → Soak

### 1. 베이스라인

단일 사용자(VU 1~2) 기준 정상 응답시간을 먼저 측정한다. 이후 부하 테스트 결과의 비교 기준으로 사용하며, 일반적인 사용자 체감 기준(500ms~1s)도 함께 참고한다.

### 2. 점진적 부하 테스트

| 단계 | VUs | 지속 시간 |
|------|-----|-----------|
| 1 | 10 | 2~3분 |
| 2 | 30 | 2~3분 |
| 3 | 50 | 2~3분 |
| 4 | 100 | 2~3분 |

시스템이 안정 상태에 도달하지 않으면 추가 연장. 최대 처리 용량이 불명확한 초기 테스트이므로 점진적으로 부하를 증가시켜 임계점을 도출한다.

### 3. 스파이크 테스트

- VUs: 10 → 100 → 10
- 전환 속도: 30초 내 즉시 전환
- 갑작스러운 트래픽 급증 상황을 재현

### 4. Soak 테스트

- VUs 30을 10분 유지
- 지속 부하 상황에서의 안정성 확인

### 테스트할 API

메모리 생성(`POST`) → 상세 조회(`GET /memory/[id]`) 세트를 사용자 트랜잭션으로 간주한다.

생성 후 앱이 바로 상세 페이지로 이동하는 실제 흐름(`router.replace('/memory/${newId}')`)을 그대로 재현한 것이다. 삭제/수정은 실제 사용 빈도가 낮아 제외했고, 리스트 조회와 상세 조회는 같은 조회로 간주했다.

## 성공/실패 기준

### 임계점 (성능 저하 시작)

| 지표 | 기준 |
|------|------|
| 지연율 | avg > 2.76s (베이스라인 2배) or p95 > 3.42s |
| 에러율 | 1~2% |
| 리소스 | CPU 70~80% 지속 |
| WebSocket | 끊김 시작 |

### 한계점 (서비스 정상 동작 불가)

| 지표 | 기준 |
|------|------|
| 지연율 | avg > 5.52s (베이스라인 4배) or p95 > 6.84s |
| 에러율 | 5% 이상 지속 |
| 리소스 | CPU 90% 이상 or OOM |
| WebSocket | 대량 끊김 시작 |

## 이관 판단 기준

### EC2 → ECS

부하 테스트 결과가 아래 기준에 해당하면 ECS 도입을 진행한다.

- CPU 지속 80% 이상
- 메모리 부족으로 컨테이너 OOM 발생
- 처리 지연으로 감정 이벤트 누락 발생

### Vercel → EC2 이전

| 증상 | 기준 |
|------|------|
| 응답 시간 급증 | 평소 200~300ms → 부하 시 2초 이상 |
| 에러율 증가 | 500 / 502 / 504 에러 증가, 요청 일부 실패 |
| 함수 timeout | 요청이 오래 걸리다 끊김, 간헐적 실패 |
| 관측 한계 도달 | 위 증상이 있는데 원인을 파악할 수 없음 |

①②③은 "문제가 생겼다"는 신호고, ④가 진짜 이관 트리거다. 증상만 있으면 코드 최적화나 설정 조정으로 해결할 수 있지만, 원인을 모르면 개선 자체가 불가능하다.

> **한 줄 기준: "문제가 생겼는데 원인을 못 찾으면 이관"**

## 예상 병목 지점

- 메모리 1GB → Python 워커 + Docker 오버헤드로 여유 적음
- Supabase Realtime WebSocket 동시 연결 수 증가 시 처리 지연 가능성

## 점진적 부하 테스트 결과 (2026-05-22)

### Vercel

| 지표 | 결과 | 임계점 기준 | 판정 |
|------|------|------------|------|
| avg | 787ms | 2,760ms | ✅ |
| p95 | 917ms | 3,420ms | ✅ |
| 에러율 | 0% | 1~2% | ✅ |
| max | 1,900ms | - | - |

create와 get의 응답시간이 거의 동일했다(785ms vs 788ms). 둘 다 Supabase DB 조회 1회라 처리 비용이 비슷하기 때문이다.

베이스라인(1.38s)보다 오히려 빠른 이유는 연속 요청으로 Vercel 함수가 항상 warm 상태를 유지했기 때문이다. 베이스라인은 수동으로 실행 간격이 있어 cold start가 섞였다.

**안정 구간 > 100 VU — Vercel은 병목이 아니다.**

### EC2

| 시각 (KST) | CPU | VU 구간 |
|-----------|-----|---------|
| 17:40 | 14% | 10~30 VU |
| 17:45 | 85% | 50~100 VU |
| 최고점 | **99%** | 100 VU |

CPU 99%로 한계점 기준(90% 이상)을 충족했다. 원인은 Python AI 워커의 LLM 호출이 동기(blocking) 방식이라 asyncio 이벤트 루프를 점유하기 때문이다. 요청이 몰리면 LLM 호출이 줄 서서 순차 처리된다.

단, Vercel API 응답시간에는 영향이 없었다. 워커는 메모리 생성 후 Supabase Realtime 이벤트로 별도 처리하는 구조라 사용자 응답과 분리되어 있다. 사용자는 체감하지 못하지만 AI 개입 메시지 생성이 지연되거나 누락됐을 가능성이 있다.

**EC2 → ECS 이관 기준 충족 (CPU 지속 80% 이상).**

### CloudWatch 5분 집계의 함정

CloudWatch는 기본 5분 단위로 집계한다. 17:40 데이터포인트는 17:35~17:40 평균이라 10~30 VU 구간이 반영되어 낮고(14%), 17:45 데이터포인트는 50~100 VU 구간이 반영되어 급등(85%)한 것처럼 보인다. 실제 CPU 상승은 단계별로 점진적이었다.

### 장애 수준 현상 및 자동 회복 불가

과부하 상태 진입 후 부하가 지속되는 동안 시스템은 자동으로 회복되지 않았다. 재부팅을 통해서만 정상 상태로 복구되었으며, 이 구간을 운영 관점에서의 장애 구간으로 정의한다.

CPU 99% 도달 시 SSM Agent도 정상 동작하지 못해 인스턴스 접속 자체가 불가능해졌다. 보안 강화를 위해 SSH 대신 AWS SSM Session Manager를 사용하는 구조였으나, CPU가 포화 상태에 이르자 SSM Agent 역시 응답하지 못했다. 과부하 시점의 상세 로그를 확인하지 못한 것도 이 때문이다.

### 지연된 포화 현상

CPU 사용률이 40분 시점까지는 약 13% 수준을 유지하다가 45분 시점에서 84%로 급격히 상승하는 구간을 확인했다. 요청이 누적되다가 특정 시점에서 처리 한계를 초과하며 부하가 급증하는 '지연된 포화 현상'이다.

이 현상은 LLM 호출이 동기(blocking) 방식이라 asyncio 이벤트 루프를 점유하기 때문에 발생한다. 요청은 비동기 task로 쌓이지만 실제 처리는 순차적으로 밀리고, 큐나 버퍼가 없어 즉시 처리를 시도하다 포화 상태에 도달한다.

### 임계점 / 한계점 재정의

| 구간 | VU | 현상 |
|------|-----|------|
| 임계점 | ~50 VU | 요청 처리 간격 증가 시작, CPU 상승 시작 |
| 한계점 | ~100 VU | CPU 99%, SSM 접속 불가, 재부팅 필요 |

### 모니터링 한계와 개선 방향

서버 내부에서 관찰하는 방식은 서버가 포화 상태일 때 관찰 도구 자체가 동작하지 않는다는 근본적인 한계가 있다. **관찰 대상과 관찰 도구는 분리해야 한다.** Grafana, Prometheus 같은 외부 모니터링 도입이 필요하다.

CloudWatch 5분 집계로는 순간적인 리소스 변화 관찰에 한계가 있다. detailed monitoring(1분 단위)을 활성화하여 동일 시나리오로 재테스트를 수행할 예정이다.

### 구조적 문제와 개선 방향

현재 구조의 문제는 세 가지다.

- **단일 워커**: 모든 요청이 한 곳에 집중됨
- **동기 LLM 호출**: asyncio 이벤트 루프 점유 → 사실상 순차 처리
- **큐/버퍼 없음**: 요청을 즉시 처리하려다 부하 급증 시 바로 포화

현재 구조의 실용 한계는 약 50 VU다.

개선 방향은 다음과 같다.

- 워커 분리: AI 처리를 별도 프로세스로 분리해 여러 개 동시 실행
- 큐/버퍼 도입: 요청을 저장해두고 워커가 하나씩 꺼내서 처리
- 스케일 가능 구조

워커 수 기준은 CPU 코어 수다. AI는 CPU를 많이 소모하는 blocking 작업이라 코어 수 기반으로 잡는다. t3.micro는 vCPU 2개이므로 워커 2~3개가 적정하다. 이 구조가 갖춰지면 ECS로의 이관이 의미 있어진다.
