## 목적

본 테스트를 통해 Vercel 및 EC2 기반 시스템의 안정 구간, 성능 저하가 시작되는 임계 구간, 그리고 서비스가 정상적으로 동작하기 어려운 한계 구간을 구분하여 분석하는 것을 목표로 한다.

## 현재 인프라 스펙

| 항목 | 값 |
|------|-----|
| 인스턴스 | t3.micro |
| vCPU | 2 |
| 메모리 | 1GB |
| 디스크 | 8GB |
| 워커 | Python AI 워커 (Docker 컨테이너) |

## 모니터링 전략

인프라 구조가 EC2와 Vercel로 나뉘어 있어 각각 다른 방식으로 성능을 판단한다.

### EC2 — 리소스 기반

EC2는 인프라에 직접 접근 가능하므로 리소스 지표로 성능을 판단한다.

| 지표 | CloudWatch 경로 |
|------|----------------|
| CPU 사용률 | AWS/EC2 → CPUUtilization |
| 메모리 사용률 | CWAgent → mem_used_percent |
| 디스크 사용률 | CWAgent → disk_used_percent |

### Vercel — 사용자 응답 기반

Vercel은 관리형 플랫폼이라 서버 리소스에 직접 접근할 수 없다. 사용자 관점의 응답 지표로 성능을 판단한다.

| 지표 | 설명 |
|------|------|
| 요청 수 | 단위 시간당 들어오는 요청 수 |
| 응답 시간 | 요청 → 응답까지 걸리는 시간 |
| 에러율 | 전체 요청 중 에러(4xx/5xx) 비율 |
| 함수 실행 시간 | Serverless Function 처리 시간 (AI 워커 연동 지연 파악 가능) |

## 관찰 지표

| 지표 | 설명 |
|------|------|
| 지연율 (avg, p95) | 평균 및 상위 5% 응답시간 |
| 에러 발생률 | 전체 요청 중 실패 비율 |
| WebSocket 끊김 빈도 | CloudWatch 로그에서 watchdog 재연결 로그 발생 여부 |
| 리소스 사용량 | EC2 CPU / 메모리 / 디스크 |

## 테스트 시나리오

### 실행 순서

베이스라인 → 점진적 부하 → 스파이크 → Soak

### 1. 베이스라인

단일 사용자(VU 1~2) 기준 정상 응답시간을 먼저 측정한다. 이후 부하 테스트 결과의 비교 기준으로 사용하며, 일반적인 사용자 체감 기준(500ms~1s)도 함께 참고한다.

### 2. 점진적 부하 테스트

| 단계 | VUs | 지속 시간 |
|------|-----|-----------|
| 1 | 10 | 2~3분 |
| 2 | 30 | 2~3분 |
| 3 | 50 | 2~3분 |
| 4 | 100 | 2~3분 |

시스템이 안정 상태에 도달하지 않으면 추가 연장. 최대 처리 용량이 불명확한 초기 테스트이므로 점진적으로 부하를 증가시켜 임계점을 도출한다.

### 3. 스파이크 테스트

- VUs: 10 → 100 → 10
- 전환 속도: 30초 내 즉시 전환
- 갑작스러운 트래픽 급증 상황을 재현

### 4. Soak 테스트

- VUs 30을 10분 유지
- 지속 부하 상황에서의 안정성 확인

### 테스트할 API

메모리 생성(`POST`) → 상세 조회(`GET /memory/[id]`) 세트를 사용자 트랜잭션으로 간주한다.

생성 후 앱이 바로 상세 페이지로 이동하는 실제 흐름(`router.replace('/memory/${newId}')`)을 그대로 재현한 것이다. 삭제/수정은 실제 사용 빈도가 낮아 제외했고, 리스트 조회와 상세 조회는 같은 조회로 간주했다.

## 성공/실패 기준

### 임계점 (성능 저하 시작)

| 지표 | 기준 |
|------|------|
| 지연율 | 베이스라인 대비 2배 이상 or p95 > 1초 |
| 에러율 | 1~2% |
| 리소스 | CPU 70~80% 지속 |
| WebSocket | 끊김 시작 |

### 한계점 (서비스 정상 동작 불가)

| 지표 | 기준 |
|------|------|
| 지연율 | 베이스라인 대비 4배 이상 or p95 > 2초 |
| 에러율 | 5% 이상 지속 |
| 리소스 | CPU 90% 이상 or OOM |
| WebSocket | 대량 끊김 시작 |

## 이관 판단 기준

### EC2 → ECS

부하 테스트 결과가 아래 기준에 해당하면 ECS 도입을 진행한다.

- CPU 지속 80% 이상
- 메모리 부족으로 컨테이너 OOM 발생
- 처리 지연으로 감정 이벤트 누락 발생

### Vercel → EC2 이전

| 증상 | 기준 |
|------|------|
| 응답 시간 급증 | 평소 200~300ms → 부하 시 2초 이상 |
| 에러율 증가 | 500 / 502 / 504 에러 증가, 요청 일부 실패 |
| 함수 timeout | 요청이 오래 걸리다 끊김, 간헐적 실패 |
| 관측 한계 도달 | 위 증상이 있는데 원인을 파악할 수 없음 |

①②③은 "문제가 생겼다"는 신호고, ④가 진짜 이관 트리거다. 증상만 있으면 코드 최적화나 설정 조정으로 해결할 수 있지만, 원인을 모르면 개선 자체가 불가능하다.

> **한 줄 기준: "문제가 생겼는데 원인을 못 찾으면 이관"**
